1. Работай в **отдельной ветке** от `main`. Меняй только файлы в `content/bridge/`
   и **одну строку** в `content/index.json`. Ничего больше не трогай.

5. Впиши уроки в `content/index.json` в этап `bridge`, прогони
   `python3 tools/validate_lessons.py` (без аргументов) и открой pull request в `main`.

## 1. Контекст проекта

Пользователь учит Python с нуля по плану из `PYTHON_PLAN.txt` (цель — удалённая работа).
В репозитории делается **веб-тренажёр**: слева список тем с чеклистом, справа теория,
задача, **пустой** редактор кода и вывод. Python исполняется прямо в браузере
(Pyodide, Python 3.14). Ученик пишет решение, нажимает «Проверить», решение
прогоняется по скрытым тестам; если все прошли — задача засчитана, тема
открывается дальше.

Работа разделена между двумя ИИ:

| Кто | Что делает | Где |
|---|---|---|
| ИИ №1 (ветка `arena/01a07075-test`) | Движок приложения, интерфейс, сохранение прогресса, уроки **этапа 1 «Основы»** (`content/basics/`) | всё, кроме `content/bridge/` |
| **ИИ №2 (ты, своя ветка)** | Уроки **этапа «Мостик»** (`content/bridge/`) | только `content/bridge/` + одна строка в `content/index.json` |

Уроки — это **чистые данные (JSON)**. Ты не пишешь ни строчки JavaScript/HTML/CSS
и не меняешь движок. Файлы, которые нужны тебе от движка, уже в репозитории:

- `engine/py/harness.py` — исполняет код ученика и сравнивает вывод с тестами.
  Приложение и валидатор используют один и тот же файл, поэтому «прошло в
  валидаторе» == «пройдёт у ученика».
- `tools/validate_lessons.py` — проверяет твои уроки. Это твой главный инструмент.
- `content/basics/01_variables.json` — эталонный урок, пример формата.
- `content/index.json` — реестр уроков по этапам.

Требуется Python 3.10+ локально (только стандартная библиотека, ничего ставить не нужно).

## 2. Кто ученик и как писать

- Взрослый новичок, русскоязычный, **прошёл этап 1**: переменные, типы, `if/elif/else`,
  `for/while`, функции (`def`, `return`, параметры по умолчанию), списки, словари,
  строковые методы (`split/join/strip/replace/upper/lower/find`), арифметика
  (`// % **`, `round/abs/min/max/sum`), файлы (`open`, `with`, режимы `r/w/a`),
  f-строки. **На эти темы опирайся свободно, но не объясняй их заново.**
- Учится в одиночку, по 1–2 часа в день. Мотивация держится на ощущении
  «я сам решил» — поэтому задачи должны быть решаемыми, а подсказки — вести,
  а не выдавать ответ.
- Тон: на «ты», спокойный, конкретный, без канцелярита и без «давайте же
  погрузимся». Короткие абзацы (2–4 предложения). Каждое понятие — сразу пример кода.
- Термины давай с английским оригиналом при первом упоминании:
  «кортеж (tuple)», «исключение (exception)». Ключевые слова и имена в тексте —
  в обратных кавычках: `try`, `len()`.
- Не выдумывай факты о Python. Если не уверен в поведении — проверь, запустив код.
  Каждый пример в теории с полем `run_check: true` валидатор **реально выполняет**
  и сверяет вывод — используй это.

## 3. Что написать: 8 уроков этапа «Мостик»

Папка `content/bridge/`, имя файла `NN_id.json`, где `NN` = `order`.
Порядок и содержание фиксированы — это то, чего не хватает ученику, чтобы войти в
любую специализацию (автоматизация, бэкенд, данные).

| order | id | Файл | Тема | Обязательно раскрыть |
|---|---|---|---|---|
| 1 | `tuples_sets` | `01_tuples_sets.json` | Кортежи и множества | tuple: создание, неизменяемость, распаковка, возврат нескольких значений из функции; set: уникальность, `add/remove/discard`, `in`, объединение/пересечение/разность, `set(list)` для удаления дублей; когда что выбирать (list vs tuple vs set) |
| 2 | `comprehensions` | `02_comprehensions.json` | Списковые включения, enumerate, zip | list comprehension с условием, dict/set comprehension кратко, `enumerate(start=)`, `zip`, `sorted(key=..., reverse=)`, `lambda` только как аргумент key, `min/max` с key |
| 3 | `exceptions` | `03_exceptions.json` | Ошибки и исключения | как читать traceback (снизу вверх), `try/except`, конкретные типы (`ValueError`, `ZeroDivisionError`, `KeyError`, `IndexError`, `FileNotFoundError`), `except ... as e`, несколько `except`, `else/finally`, `raise`, «не лови всё подряд голым except» |
| 4 | `modules` | `04_modules.json` | Модули и импорт | `import`, `from ... import`, `as`, свои модули (файл `.py` рядом), `if __name__ == "__main__":`, где искать документацию, `dir()/help()` |
| 5 | `stdlib` | `05_stdlib.json` | Стандартная библиотека | `random` (`randint/choice/shuffle/seed`), `math` (`sqrt/ceil/floor/pi`), `datetime` (`date.today()`, `datetime`, `timedelta`, `strftime/strptime`), `os.path`/`pathlib.Path` (`exists`, `suffix`, `name`, `iterdir` кратко), `time` кратко |
| 6 | `json_csv` | `06_json_csv.json` | JSON и CSV | `json.dumps/loads`, `json.dump/load` с файлами, `ensure_ascii=False`, `indent`; `csv.reader/writer`, `DictReader/DictWriter`, `newline=""`, `encoding="utf-8"`; типичная задача «прочитать CSV → посчитать → записать JSON» |
| 7 | `oop_basics` | `07_oop_basics.json` | Основы ООП | зачем классы, `class`, `__init__`, `self`, атрибуты и методы, `__str__`, несколько объектов одного класса, наследование в 1 пример, «читать чужой код с классами» как цель, без метаклассов/дескрипторов/property |
| 8 | `functions_advanced` | `08_functions_advanced.json` | Функции: продвинутое + стиль | `*args`, `**kwargs`, аргументы по имени, изменяемые значения по умолчанию (ловушка `def f(x=[])`), докстринги, аннотации типов кратко, PEP 8: имена, отступы, длина строки, пробелы вокруг операторов, «одна функция — одно дело» |

Объём каждого урока: **теория 1500–5000 символов**, **3–4 задачи** (сложность 1 → 2 → 3),
**3–6 тестов** на задачу, минимум один `visible: true`.

Не пиши уроки про Django/FastAPI/pandas/aiogram/requests — это следующие этапы и
других библиотек в тренажёре нет (только стандартная библиотека Python).

## 4. Формат файла урока

Кодировка UTF-8, отступ 2 пробела, `ensure_ascii=False` (кириллица как есть, не `\u043f`).
Все поля обязательны, если не сказано «необязательно».

```jsonc
{
  "id": "tuples_sets",              // snake_case латиницей; == имя файла без NN_
  "stage": "bridge",                // всегда "bridge" для твоих уроков
  "order": 1,                       // порядковый номер внутри этапа == NN в имени файла
  "title": "Кортежи и множества",   // до 40 символов
  "subtitle": "Когда список — не лучший выбор",   // одна строка, до 80 символов
  "minutes": 45,                    // ориентировочное время, 20–60
  "version": 1,                     // всегда 1 для нового урока
  "goals": [ "…", "…", "…" ],       // 2–5 пунктов «после урока я умею…», глаголами
  "theory": [ /* блоки, см. 4.1 */ ],
  "tasks":  [ /* задачи, см. 4.2 */ ],
  "summary": [ "…", "…" ],          // 3–5 коротких пунктов «что запомнить»
  "further": [ "…" ]                // необязательно: 1–3 ссылки/названия для чтения
}
```

### 4.1. Блоки теории (`theory`)

Массив объектов, порядок = порядок отображения. Типы:

| type | Поля | Назначение |
|---|---|---|
| `text` | `text` | Абзац. Допустима лёгкая разметка: `` `код` ``, **жирный**. Без заголовков `#`, без HTML. |
| `code` | `code`, `output` (необяз.), `input` (необяз.), `run_check` (необяз., bool), `allow_invalid` (необяз., bool), `caption` (необяз.) | Пример кода. Если указан `output` и `run_check: true`, валидатор **запустит код и сверит вывод** — ставь это везде, где вывод детерминирован. `input` — строка, подаваемая в `input()` при проверке. `allow_invalid: true` — только если код намеренно содержит синтаксическую ошибку (показываем, как выглядит ошибка). |
| `note` | `text` | Врезка «обрати внимание» (зелёная). |
| `warning` | `text` | Врезка «частая ошибка / ловушка» (жёлтая). |
| `table` | `header` (список строк), `rows` (список списков строк) | Таблица: сравнение методов, типов и т. п. |
| `list` | `items` (список строк), `title` (необяз.) | Маркированный список. |
| `compare` | `title` (необяз.), `bad`, `good` | Два фрагмента кода рядом: «так не надо» / «так надо». |

Правила теории:
- Начинай с **«зачем это нужно»** в одном абзаце и живого примера, а не с определения.
- Один блок `text` — одна мысль. После каждой новой конструкции — блок `code`.
- Примеры кода — **короткие (3–10 строк), запускаемые, с осмысленными данными**
  (не `foo/bar`, а `prices`, `users`, `filename`).
- В примерах с `random`, `datetime.now()` и т. п. вывод недетерминирован — либо
  не указывай `output`, либо укажи и **не ставь** `run_check` (или используй
  `random.seed(...)` — тогда `run_check` можно).
- Минимум одна врезка `warning` на типичную ошибку новичка в этой теме.
- Никаких «умных» кавычек `« » “ ”` **внутри кода**. В тексте — можно.

### 4.2. Задачи (`tasks`)

```jsonc
{
  "id": "tuples_sets_t1",            // <id урока>_t<N>, N от 1
  "title": "Уникальные слова",       // до 40 символов
  "difficulty": 1,                   // 1 — прямое применение, 2 — комбинация, 3 — мини-проект
  "statement": "…",                  // условие: что дано, что сделать, что вывести. 2–6 предложений
  "input_format": "…",               // что и в каком порядке читается через input()
  "output_format": "…",              // что и в каком формате печатать — точно, до символа
  "examples": [ {"input": "…", "output": "…"} ],   // 1–2 примера для показа; обычно = visible-тесты
  "hints": [ "…", "…", "…" ],        // 2–3 подсказки: от общей идеи к почти-решению, без готового кода
  "tests": [ /* см. 4.3 */ ],
  "checks": { "must_use": [], "must_not_use": [], "must_define": [] },   // необязательно
  "compare": "exact",                // необязательно: "exact" (по умолчанию) или "tokens"
  "solution": "…",                   // эталонное решение — ОБЯЗАТЕЛЬНО, прогоняется валидатором
  "wrong_solution": "…",             // необязательно, но очень желательно: типичное НЕВЕРНОЕ решение,
                                     // которое тесты обязаны завалить (проверка силы тестов)
  "note": "…"                        // необязательно: заметка автора, ученику не показывается
}
```

- `starter_code` **не использовать**: по требованию проекта редактор ученика должен
  быть пуст. Задачи «допиши функцию» формулируй словами: «Определи функцию `area(a, b)`,
  которая…» и вызывай её из `code_after` теста.
- `checks.must_use` / `must_not_use` — имена, ключевые слова, операторы или `"f-string"`.
  Проверяется по токенам кода (строки и комментарии не считаются). Используй, чтобы
  задача действительно тренировала тему: например, в уроке про множества
  `must_use: ["set"]`, в задаче на comprehension `must_not_use: ["append"]`.
- `checks.must_define` — имена функций/классов, которые ученик обязан определить.
- `compare: "tokens"` — сравнение по «словам» с допуском для чисел (1e-6). Для задач,
  где выводятся дробные числа после вычислений. По умолчанию `exact`: построчно,
  пробелы в конце строк и пустые строки в конце игнорируются, остальное — точно.

### 4.3. Тесты (`tests`)

```jsonc
{
  "input": "3\nа б в",               // строки для input(), разделитель \n; необязательно (по умолчанию "")
  "output": "3",                     // ожидаемый вывод (stdout). Обязателен, если нет output_files
  "visible": true,                   // показывать ученику как пример; хотя бы один на задачу
  "files": {"data.txt": "1\n2\n"},   // необязательно: файлы, создаваемые в рабочей папке ДО запуска
  "output_files": {"out.txt": "3"},  // необязательно: файлы, которые программа должна создать, и их содержимое
  "code_before": "…",                // необязательно: код, выполняемый ДО кода ученика (подготовка данных)
  "code_after": "print(area(2, 3))", // необязательно: код, выполняемый ПОСЛЕ (вызов функции ученика)
  "note": "граничный случай: пустой ввод"   // необязательно
}
```

Как устроено выполнение (важно для понимания, что можно проверять):
- Код ученика выполняется как файл `main.py` в **пустой временной папке**; туда заранее
  записаны `files`. Можно читать/писать файлы, `import` файлов из `files` работает
  (`files: {"helpers.py": "…"}` → в коде ученика `import helpers`).
- `code_before`, код ученика и `code_after` выполняются **в одном пространстве имён**
  по очереди. Значит, `code_after` видит функции и переменные ученика.
- `input()` читает строки из `input` теста. Лишний `input()` → `EOFError` → тест не пройден.
  Подсказки внутри `input("Введите: ")` в режиме проверки в вывод **не попадают** —
  ученик может писать их свободно.
- Доступна только стандартная библиотека. Нет сети, нет `pip`.
- Лимит вывода 200 000 символов, лимит времени ~5 с на тест (устанавливает приложение).

Правила составления тестов:
1. **3–6 тестов** на задачу. Первый — из примера в условии (`visible: true`).
2. Обязательно **граничные случаи**: пустой ввод/список, один элемент, ноль,
   отрицательное число, повторяющиеся элементы, регистр букв, пробелы по краям —
   то, что относится к задаче.
3. Ожидаемые выводы тестов должны **различаться** между собой, иначе пройдёт
   `print("константа")`.
4. Тесты должны заваливать типичное неверное решение — запиши его в `wrong_solution`
   и убедись, что валидатор не ругается.
5. Если задача про функцию — проверяй через `code_after` с `print(...)` результата,
   а не только через вывод внутри функции. Проверь `must_define`.
6. Вывод дробных чисел: всегда фиксируй формат в условии (`:.2f`) или ставь
   `compare: "tokens"`. Не оставляй `0.30000000000000004` на совести ученика.
7. Если задача про файлы — используй `files` для входного файла и `output_files`
   для проверки результата. Имена файлов — латиницей, `.txt/.csv/.json`.
8. Не используй в тестах текущую дату, `random` без `seed` и всё, что даёт разный
   результат при повторном запуске.
9. Порядок обхода `set` не гарантирован — в задачах на множества требуй **отсортированный**
   вывод (`sorted(...)`) и укажи это в условии.

### 4.5. Пример задачи с файлами

```json
{
  "id": "json_csv_t3",
  "title": "Итоги продаж в JSON",
  "difficulty": 3,
  "statement": "В файле `sales.csv` строки вида `товар;количество;цена` (первая строка — заголовок). Посчитай выручку по каждому товару (количество × цена, суммируя одинаковые товары) и запиши результат в `report.json` как словарь {товар: выручка}, отсортированный по названию товара, с отступом 2 и кириллицей как есть. Выручку округли до 2 знаков. Ничего не печатай.",
  "input_format": "Ввода нет. Данные — в файле sales.csv в рабочей папке.",
  "output_format": "Файл report.json.",
  "examples": [{"input": "sales.csv:\nтовар;количество;цена\nКофе;2;150\nЧай;1;80\nКофе;1;150", "output": "report.json:\n{\n  \"Кофе\": 450.0,\n  \"Чай\": 80.0\n}"}],
  "hints": [
```

## 5. Проверка — обязательная часть работы

```bash
# один урок
python3 tools/validate_lessons.py content/bridge/03_exceptions.json

# все твои уроки
python3 tools/validate_lessons.py content/bridge/*.json

# всё, что подключено в index.json (перед сдачей) — предупреждения считаются ошибками
python3 tools/validate_lessons.py --strict
```

Что делает валидатор и что означают сообщения:

| Сообщение | Причина | Что делать |
|---|---|---|
| `эталонное решение НЕ проходит тест` | `solution` даёт не тот вывод, что в `output` теста | Запусти `solution` руками с этим вводом; исправь либо тест, либо решение. Обычно — лишний пробел, перевод строки, формат числа |
| `программа pass проходит все тесты` | у тестов пустой `output` и нет `output_files`/`code_after` | Тесты ничего не проверяют — добавь ожидаемый вывод |
| `wrong_solution проходит все тесты` | тесты слабые | Добавь тест, который ловит именно эту ошибку |
| `эталонное решение нарушает собственные checks` | `must_use` требует то, чего нет в `solution` | Поправь `checks` или `solution` |
| `ни один тест не помечен visible` | ученику нечего показать как пример | Поставь `visible: true` первому тесту |
| `в примере кода есть «умная» кавычка` | `«»“”` внутри `code`/`solution` | Замени на `"` |
| `пример кода не компилируется` | ошибка в `theory[].code` | Исправь или поставь `allow_invalid: true`, если ошибка показана намеренно |
| `вывод примера не совпадает с указанным` | `output` в теории не совпадает с реальным | Исправь `output` — не ври ученику |
| `[предупреждение] …` | стиль/полнота | Исправь по возможности; при `--strict` они блокируют сдачу |

Дополнительно к валидатору **прочитай каждый урок глазами** как ученик:
понятно ли условие без подглядывания в тесты? Совпадает ли формат вывода
в условии с тестами до символа? Не решается ли задача 3 без знаний из урока 5?

## 6. Чего делать НЕЛЬЗЯ

- Менять что-либо вне `content/bridge/` и одной строки в `content/index.json`
  (в том числе `harness.py`, `validate_lessons.py`, `content/basics/`, `PYTHON_PLAN.txt`).

- Использовать `starter_code`.
- Ссылаться на внешние библиотеки (`requests`, `pandas`, `aiogram`, `numpy`…).
- Писать задачи, где вывод зависит от времени, случайности без `seed`, порядка `set`/`dict`
  без сортировки, локали.
- Копировать чужие задачи с Stepik/LeetCode дословно. Формулируй свои, на бытовых
  и рабочих данных (покупки, оценки, файлы, расписание, логи).
- Оставлять в JSON комментарии `//` — реальный JSON их не допускает (в этом документе
  они только для пояснения).

## 7. Порядок работы и сдача

1. Создай ветку от актуального `main`, например `content/bridge-lessons`.
2. Изучи `content/basics/01_variables.json` и запусти
   `python3 tools/validate_lessons.py` — убедись, что окружение работает (`РЕЗУЛЬТАТ: OK`).
3. Пиши уроки **по одному, в порядке таблицы из раздела 3**. После каждого —
   валидатор, затем самопроверка глазами (раздел 5). Коммить каждый урок отдельно:
   `content: bridge 03 exceptions`.
4. После всех восьми — впиши их в `content/index.json`:
   ```json
   {
     "id": "bridge",
     "title": "Мостик — от основ к специализации",
     "description": "…",
     "lessons": [
       "bridge/01_tuples_sets.json",
       "bridge/02_comprehensions.json",
       "bridge/03_exceptions.json",
       "bridge/04_modules.json",
       "bridge/05_stdlib.json",
       "bridge/06_json_csv.json",
       "bridge/07_oop_basics.json",
       "bridge/08_functions_advanced.json"
     ]
   }
   ```
   Остальное содержимое `index.json` не трогай (этап `basics` заполняет ИИ №1;
   если при слиянии будет конфликт в этом файле — он тривиальный, оставляются оба списка).
5. Финальная проверка: `python3 tools/validate_lessons.py --strict` → `РЕЗУЛЬТАТ: OK`.
6. Открой pull request в `main`. В описании PR обязательно:
   - таблица «урок → количество задач → символов теории»;
   - вывод валидатора (последние 4 строки);
   - список сомнений/вопросов, если есть (например, «в уроке 5 не уверен, что
     `pathlib` нужен новичку — оставил кратко»);
   - замечания к движку/валидатору, если нашёл.
7. Не сливай PR сам — пользователь посмотрит результат и сольёт.

## 9. Если что-то пошло не так

- Валидатор падает с traceback (не с `[ОШИБКА]`) — это баг валидатора или битый JSON.
  Сначала проверь JSON: `python3 -m json.tool content/bridge/NN_id.json`.
  Если JSON валиден — опиши проблему в PR, не правь `tools/`.
- Нужен приём, которого нет в формате (например, картинка) — не нужен. Объясни текстом
  и таблицей.
- Кажется, что 8 уроков — много или мало — делай 8. Объём одного урока можно
  варьировать в пределах раздела 3.
- Сомневаешься в формулировке — выбери более простую и однозначную. Ученик один,
  переспросить ему не у кого.
